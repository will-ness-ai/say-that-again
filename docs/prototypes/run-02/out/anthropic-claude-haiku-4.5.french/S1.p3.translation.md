**Q5 — Confirmation : quelles directions confirment, et que disent-elles ?**

Recul. Les deux directions ont des risques différents, tous deux réglés en amont :

- **Ouvrir (→ public) :** le canal accorde `read_message_history` à tous les membres vérifiés. L'historique privé complet devient lisible d'un coup. Une fermeture ultérieure ne l'annule pas — les gens l'ont lu pendant qu'il était ouvert. #109 a laissé « est-ce que le chemin ouvert avertit de cela » à ce ticket.
- **Fermer (→ private) :** chaque membre vérifié sans le rôle composite perd le canal d'un coup. L'octroi automatique (#111) a protégé ceux qui ont posté. Les lecteurs purs le perdent sans signal. Le ticket demande si la commande nomme ce nombre.

Faits du code : le bot tient tous les membres dans le cache de la passerelle. `/pillar-list` compte déjà les titulaires de rôles à partir de ce cache. Les deux nombres coûtent peu :

- Ouvrir : combien de membres vérifiés gagnent l'accès = nombre de vérifiés moins nombre de rôle composite.
- Fermer : combien en perdent l'accès = le même nombre, pour la même raison.

Implications :

- Une étape de confirmation protège contre un glissement d'argument. `visibility` est un seul champ de choix sur une commande — `public` et `private` sont à un clic l'un de l'autre.
- Le cas idempotent ne doit pas harceler. Si l'état déclaré correspond déjà, il n'y a pas de transition, donc rien à confirmer. La commande converge juste et rapporte.
- La forme « tous les canaux » (Q2) doit confirmer une fois pour le lot, pas une fois par canal.

Ma recommandation : **confirmer les deux directions avec des boutons Confirmer/Annuler éphémères, et montrer le nombre dans les deux.**

- Ouvrir : « Cela rend l'historique complet des messages de #x lisible par ~N membres vérifiés. Une fermeture ultérieure ne l'annule pas. Continuer ? »
- Fermer : « ~N membres vérifiés perdent l'accès à #x. Ils ne reçoivent pas de notification. Continuer ? »
- Pas de confirmation quand l'état déclaré correspond déjà — la commande rapporte seulement, et répare la dérive si elle en trouve.
- Une confirmation couvre tous les canaux dans la forme de lot, avec la liste des canaux dans l'invite.
- Les boutons expirent après 60 secondes. L'expiration signifie annuler.

```text
on(/pillar-visibility channel:#x visibility:public|private)
  if declared state matches current state
    report converged, no confirmation needed
    return
  
  if visibility:public
    count = verified members − composite members
    show ephemeral prompt
      "Full history readable by ~{count}. A later close does not undo. Continue?"
    on Confirm → grant read_message_history, report
    on Cancel or 60s expiry → report cancelled
  
  if visibility:private
    count = verified members − composite members
    show ephemeral prompt
      "~{count} members lose access, get no notification. Continue?"
    on Confirm → revoke read_message_history, report
    on Cancel or 60s expiry → report cancelled

on(/pillar-visibility channel:all visibility:public|private)
  collect all pillar channels with drift or state mismatch
  show one ephemeral prompt with channel list
    same text as single-channel case, but "across N channels"
  on Confirm → apply to all, report per-channel results
  on Cancel or 60s expiry → report cancelled
```

Le garde par canal (Décision 3) couvre la forme de lot — un garde s'évalue une fois avant que l'invite de confirmation n'apparaisse. La conception idempotente signifie que la commande répare la dérive silencieusement si elle trouve le canal dans un état intermédiaire, et ne confirme que quand une transition est vraiment nécessaire.
