**Q5 — Confirmation : quelles directions confirment, et que disent-elles ?**

Recul. Les deux directions ont des risques différents, tous deux réglés en amont :

- **Ouvrir (→ public) :** le canal donne `read_message_history` à tous les membres vérifiés. L'historique privé complet devient lisible d'un coup. Une fermeture ultérieure ne le retire pas — les gens l'ont lu pendant qu'il était ouvert. #109 a laissé « le chemin ouvert avertit-il de cela » à ce ticket.
- **Fermer (→ private) :** chaque membre vérifié sans le rôle composite perd le canal d'un coup. L'octroi automatique (#111) a protégé ceux qui ont posté. Les lecteurs purs le perdent sans signal. Le ticket demande si la commande nomme ce nombre.

Faits du code : le bot tient tous les membres dans le cache de la passerelle. `/pillar-list` compte déjà les titulaires de rôles à partir de ce cache. Les deux nombres coûtent peu :

- Ouvrir : combien de membres vérifiés gagnent l'accès = nombre vérifié moins nombre de rôle composite.
- Fermer : combien le perdent = le même nombre, pour la même raison.

Conséquences :

- Une étape de confirmation protège contre un glissement d'argument. `visibility` est un seul champ de choix sur une seule commande — `public` et `private` sont à un clic l'un de l'autre.
- Le cas idempotent ne doit pas harceler. Si l'état déclaré correspond déjà, il n'y a pas de transition, donc rien à confirmer. La commande converge juste et rapporte.
- La forme « tous les canaux » (Q2) doit confirmer une fois pour le lot, pas une fois par canal.

Ma recommandation : **confirmer les deux directions avec des boutons Confirmer/Annuler éphémères, et montrer le nombre dans les deux.**

- Ouvrir : « Cela rend l'historique complet des messages de #x lisible par ~N membres vérifiés. Une fermeture ultérieure ne défait pas cela. Continuer ? »
- Fermer : « ~N membres vérifiés perdent l'accès à #x. Ils ne reçoivent pas de notification. Continuer ? »
- Pas de confirmation quand l'état déclaré correspond déjà — la commande rapporte seulement, et répare la dérive si elle en trouve.
- Une confirmation couvre tous les canaux dans la forme de lot, avec la liste des canaux dans l'invite.
- Les boutons expirent après 60 secondes. L'expiration signifie annuler.

Logique de confirmation et ses deux cas :

```text
on(/pillar-visibility)
  si l'état déclaré correspond à l'état actuel
    rapporter la convergence
    retour
  
  si la direction est ouvrir (→ public)
    nombre = membres vérifiés − membres composite
    invite : « Rend l'historique lisible par ~{nombre}. La fermeture ultérieure ne défait pas. Continuer ? »
    on(Confirmer) → accorder read_message_history, rapporter
    on(Annuler ou 60s) → fermer
  
  si la direction est fermer (→ private)
    nombre = membres vérifiés − membres composite
    invite : « ~{nombre} membres perdent l'accès. Pas de notification envoyée. Continuer ? »
    on(Confirmer) → révoquer read_message_history, rapporter
    on(Annuler ou 60s) → fermer

on(/pillar-visibility channel:all)
  collecter toutes les transitions (les idempotentes filtrées)
  si des transitions existent
    compter le total des membres affectés sur tous les canaux
    invite : « Affecte ~{nombre} membres sur {N} canaux. Continuer ? »
    on(Confirmer) → appliquer tous, rapporter par canal
    on(Annuler ou 60s) → fermer
```

Pourquoi les deux directions ont besoin de confirmation :

```text
ouvrir (→ public)
  ✓ bon marché : vérifié − composite déjà compté par /pillar-list
  ✗ irréversible : l'historique lisible maintenant reste lisible après fermeture
  → avertir de l'asymétrie

fermer (→ private)
  ✓ bon marché : même nombre
  ✗ silencieux : les membres perdent l'accès sans notification
  → nommer le nombre pour que l'opérateur connaisse l'étendue
```
