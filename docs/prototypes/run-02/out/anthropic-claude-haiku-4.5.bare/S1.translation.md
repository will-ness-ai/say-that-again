## Q5 — Confirmation: What should we ask, and what should we say?

Step back. Opening and closing a channel both carry real risks. Both risks happen before the user acts:

- **Open (→ public):** When you open a channel, all verified members can suddenly read the entire message history. Once you close it later, that history stays readable — people saw it while it was open. Ticket #109 asked: should we warn about this first?

- **Close (→ private):** When you close a channel, every verified member who doesn't have the special role loses access right away. Auto-grant (#111) kept people who posted there. But people who only read it? They lose access with no warning. The ticket asks: should we name this in the command?

The code gives us cheap numbers. The bot keeps all members in its cache. The `/pillar-list` command already counts role holders from that cache. So we can show both numbers with no cost:

- Open: verified members who gain access = all verified members minus those with the special role.
- Close: verified members who lose access = the same number, for the same reason.

Why confirmation matters:

- One click can slip. `visibility` is one field on one command — `public` and `private` are one click apart.
- Don't ask twice for the same state. If the channel is already public and you ask to make it public, skip the question. Just confirm it's done.
- For batch operations (Q2), ask once for all channels, not once per channel.

My suggestion: **Ask both directions with Confirm and Cancel buttons. Show the number in both.**

- Skip the question if the state already matches. Just run the command and report the result. Fix any drift you find.
- For batch operations, one confirmation covers all channels. Show the channel list in the prompt.
- Buttons disappear after 60 seconds. When they expire, treat it as cancel.
