replaces: the confirmation logic and its two cases

```text
on(/pillar-visibility)
  if declared state matches current state
    report convergence
    return
  
  if direction is open (→ public)
    count = verified members − composite members
    prompt: "Makes history readable by ~{count}. Later close won't undo. Continue?"
    on(Confirm) → set public, report
    on(Cancel) → report cancelled
    on(60s timeout) → cancel
  
  if direction is close (→ private)
    count = verified members − composite members
    prompt: "~{count} members lose access, no notification. Continue?"
    on(Confirm) → set private, report
    on(Cancel) → report cancelled
    on(60s timeout) → cancel

on(/pillar-visibility channel:all ...)
  collect all channels that need transition
  if none
    report all already match
    return
  
  count = verified members − composite members
  prompt: "Affects {channel_count} channels, ~{count} members per channel. Continue?"
  on(Confirm) → apply to all, report each
  on(Cancel) → report cancelled
  on(60s timeout) → cancel
```

supplements: why both directions need confirmation

```text
Open (→ public)
  ├─ Danger: full history becomes readable to all verified
  └─ Irreversible: later close does not retract reads already made

Close (→ private)
  ├─ Danger: verified members lose access with no signal
  └─ Silent: they get no notification of removal
```

supplements: why the count is cheap

```text
/pillar-list already reads from gateway cache:
  verified.members.size          ← role holder count, no API call
  composite.members.size         ← role holder count, no API call

Both directions use the same count:
  members who gain/lose access = verified − composite
```
