# Confirmation for Pillar Visibility

Decision 4 is recorded: per-channel badge on each list line, both states labeled.

---

**Q5 — Confirmation: which directions confirm, and what do they say?**

The two directions carry different risks, both already decided:

- **Open (→ public):** grants `read_message_history` to all verified members. The full private history becomes readable at once. A later close does not retract it — people read it while it was open. #109 asked if the open path warns about this.
- **Close (→ private):** every verified member without the composite role loses the channel at once. Auto-grant (#111) protected the people who posted. Pure readers lose it with no signal. The ticket asks if the command names that number.

The bot holds all members in the gateway cache. `/pillar-list` already counts role holders from that cache. Both counts are cheap:

- Open: verified count minus composite-role count = how many gain access.
- Close: verified count minus composite-role count = how many lose access.

A confirmation step protects against an argument slip. `visibility` is one choice field on one command — `public` and `private` sit one click apart. The idempotent case must not nag. If the declared state already matches, there is no transition, so there is nothing to confirm. The command converges and reports. The "all channels" form (Q2) confirms once for the batch, not once per channel.

---

**Confirmation logic and its two cases**

```text
on(/pillar-visibility channel:#x visibility:public|private)
  if declared state matches current state
    report convergence
    return
  
  if visibility:public
    count = verified members minus composite-role members
    prompt: "This makes history readable by ~{count}. A later close does not undo that. Continue?"
    on(Confirm)
      grant read_message_history to verified role
      report success
    on(Cancel or 60s expiry)
      report cancelled
  
  if visibility:private
    count = verified members minus composite-role members
    prompt: "~{count} members lose access to #x. They get no notification. Continue?"
    on(Confirm)
      revoke read_message_history from verified role
      report success
    on(Cancel or 60s expiry)
      report cancelled

on(/pillar-visibility channel:all visibility:public|private)
  channels = all pillar channels with mismatched state
  if channels is empty
    report all converged
    return
  
  count = verified members minus composite-role members
  prompt: "Apply to {channels.length} channels. ~{count} members per channel [open|lose access]. Continue?"
  on(Confirm)
    for each channel
      apply visibility change
    report batch success
  on(Cancel or 60s expiry)
    report cancelled
```

---

**Why both directions need confirmation**

| Direction | Danger | Scope | Guard |
|-----------|--------|-------|-------|
| Open (→ public) | Grants `read_message_history` to all verified | Full private history readable at once | Confirm with count of members gaining access |
| Close (→ private) | Revokes channel access from verified without composite role | Pure readers lose it with no signal | Confirm with count of members losing access |

---

My recommendation: **confirm both directions with ephemeral Confirm/Cancel buttons, and show the number in both.**

- Open: "This makes the full message history of #x readable by ~N verified members. A later close does not undo that. Continue?"
- Close: "~N verified members lose access to #x. They get no notification. Continue?"
- No confirmation when the declared state already matches — the command only reports, and repairs drift if it finds some.
- One confirmation covers all channels in the batch form, with the channel list in the prompt.
- The buttons expire after 60 seconds. Expiry means cancel.
