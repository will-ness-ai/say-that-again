**Q5 — Confirmation: which directions confirm, and what do they say?**

Step back. The two directions have different risks, both known already:

- **Open (→ public):** the channel gives `read_message_history` to all verified members. The full private history becomes readable right away. A later close does not take it back — people read it while it was open. Ticket #109 asked if the open path warns about this.
- **Close (→ private):** every verified member without the composite role loses the channel right away. Auto-grant (#111) kept the people who posted. Pure readers lose it with no message. This ticket asks if the command shows that number.

Facts from the code: the bot holds all members in the gateway cache. `/pillar-list` already counts role holders from that cache. So both counts are fast:

- Open: how many verified members gain access = verified count minus composite-role count.
- Close: how many lose access = the same number, for the same reason.

Why this matters:

- A confirmation step stops a slip of the hand. `visibility` is one choice field on one command — `public` and `private` sit one click apart.
- The idempotent case must not ask. If the declared state already matches, there is no change, so there is nothing to confirm. The command just moves to the target state and reports.
- The "all channels" form (Q2) must confirm once for the batch, not once per channel.

My recommendation: **confirm both directions with ephemeral Confirm/Cancel buttons, and show the number in both.**

- Open: "This makes the full message history of #x readable by ~N verified members. A later close does not undo that. Continue?"
- Close: "~N verified members lose access to #x. They get no notification. Continue?"
- No confirmation when the declared state already matches — the command only reports, and fixes drift if it finds some.
- One confirmation covers all channels in the batch form, with the channel list in the prompt.
- The buttons expire after 60 seconds. Expiry means cancel.
