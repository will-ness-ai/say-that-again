**Q5 — Confirmation: which directions confirm, and what do they say?**

The two directions have different dangers, both already decided upstream:

- **Open (→ public):** the channel grants `read_message_history` to all verified members. The full private history becomes readable at once. A later close does not take it back — people read it while it was open. #109 asked whether the open path should warn about this.
- **Close (→ private):** every verified member without the composite role loses the channel at once. Auto-grant (#111) protected the people who posted. Pure readers lose it with no signal. The ticket asks if the command shows that number.

The bot holds all members in the gateway cache. `/pillar-list` already counts role holders from that cache. So both counts are free:

- Open: how many verified members gain access = verified count minus composite-role count.
- Close: how many lose access = the same number, for the same reason.

Three things matter:

- A confirmation step protects against an argument slip. `visibility` is one choice field on one command — `public` and `private` sit one click apart.
- The idempotent case must not ask. If the declared state already matches, there is no transition, so there is nothing to confirm. The command just converges and reports.
- The "all channels" form (Q2) must confirm once for the batch, not once per channel.

My recommendation: **confirm both directions with ephemeral Confirm/Cancel buttons, and show the number in both.**

On declared state matches current state
: report convergence and return

On open (→ public)
: count = verified members − composite members
: prompt: "This makes the full message history of #x readable by ~{count} verified members. A later close does not undo that. Continue?"
: Confirm button → grant `read_message_history`, report
: Cancel button or 60 second timeout → report cancellation

On close (→ private)
: count = verified members − composite members
: prompt: "~{count} verified members lose access to #x. They get no notification. Continue?"
: Confirm button → revoke `read_message_history`, report
: Cancel button or 60 second timeout → report cancellation

On batch form (channel: all)
: count total members across all channels
: prompt: "This affects ~{count} members across {N} channels. Continue?"
: Confirm button → apply to all, report per-channel
: Cancel button or 60 second timeout → report cancellation
